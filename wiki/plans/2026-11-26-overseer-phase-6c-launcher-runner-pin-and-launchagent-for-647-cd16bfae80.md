# Overseer phase 6c — launcher, runner pin and LaunchAgent for #647

Deliver a person-set release pin, a macOS installer and an independently installed launcher for one observe-only pass. Target the v1 release format at `ddc18dc`, Node 24.14.0 and pnpm 10.34.9. Live installation and activation belong to a later session. Forwarding and notices belong to 6d, failure breakers to phase 10, and autonomous pin promotion, fallback and launcher protection to phase 11. Phase 5 repair code and the Office repair-resume switch are outside this change.

## One launcher invocation

- [ ] Implement `scripts/overseer-launch.mjs` as one installed ES module invoked with Node. Import Node built-ins only, guard the direct entry point and export the writer, validator and other functions needed by focused tests. Install SIGTERM, SIGINT and SIGHUP handling before recovery or dispatch. A shutdown request prevents further dispatch in that invocation.
- [ ] Acquire `control/launcher.lock` before reading launcher state. Follow `acquirePassLock()`’s exclusive acquisition-guard pattern with a launcher UUID, positive PID and OS start identity. Reclaim only after a positive-PID probe returns `ESRCH` and a reread under the guard identifies the same owner. A live or reused PID, inconclusive probe, unreadable owner or leftover guard blocks acquisition. The losing invocation leaves the first pass and its state alone. Release only the lock still naming this owner, after final publication.
- [ ] Give the built-in writer and TypeScript reader one bounded v1 file contract. The exact top-level keys are `version`, `current`, `consecutiveFailures`, `counts`, `last` and `recent`. Use closed outcome kinds, nonnegative safe integer counts and durations, ISO timestamps, bounded strings, nullable `last` and the latest 20 history records. `current` records the attempt UUID, pinned commit and entry, start, deadline, phase, leader PID, PGID, OS start identity, counting decision and latest bounded observation. `starting` has null process identity. A registered leader requires equal PID and PGID from 2 through 2147483647 and a valid start identity. A counted attempt can still be current while cleanup is pending. Reject unknown keys and malformed variants. Only a missing state file represents empty state.
- [ ] Publish state and ownership records using `publishDurable` in `server/release/durable-file.ts` as the reference. Write complete bytes to an exclusive sibling draft, check the write length, sync and close, publish atomically, and sync the parent directory. A failed prerequisite save prevents dispatch. A later publication error triggers cleanup of owned work and a diagnostic, with recovery based on the last durable record.
- [ ] Recover `current` before checking the next deadline, URL or pin. An unregistered `starting` record blocks for inspection. For registered groups follow `probeProcessGroup` semantics. `ESRCH` proves absence, a successful probe proves presence, and every other error is inconclusive. Validate PID range and PID/PGID equality again immediately before every negative-PID probe or signal.
- [ ] For a present group, use bounded `/bin/ps` reads under `LC_ALL=C`. Follow `groupInventory` for PID, PGID, normalized `lstart`, bounded member identities and completeness. Check the leader’s invocation for the installed helper and the exact `--group` UUID. Save only the bounded observation and its time. A missing leader, mismatched identity, incomplete inventory or failed observation retains `current`, withholds signals and blocks a successor. Recheck ownership before TERM and before KILL. Settle an unaccounted vanished attempt as `lost` and a surviving interrupted attempt as `orphan` once. Honor any previously saved counting decision. Clear a registered attempt only on confirmed group absence.
- [ ] After recovery, require `OVERSEER_PASS_DEADLINE_MS` to contain decimal digits representing a safe integer from 30000 through 900000 inclusive. Validate an optional `OVERSEER_OFFICE_URL` against `officeUrl()`’s bare loopback HTTP rule. A configuration refusal on a safe root counts once as `config`. - [ ] Read one strict pin snapshot. Require the physical directory to equal `<effective Office data root>/releases/<commit>` and the same covered physical entry required at pin time. ## Dispatch, shutdown and counting

- [ ] Create an attempt UUID and durably save `current` as `starting` before spawning. Start the monotonic pass deadline at dispatch, including startup. Spawn a temporary detached `--group <UUID>` mode of the same installed script. Attach error, exit, IPC and output listeners immediately. The helper waits for authorization over private parent IPC. The parent observes and durably registers its PID, PGID and OS start identity before authorizing candidate execution. A disconnect before authorization makes the helper exit. A failed registration withholds authorization and stops the helper. A definitive spawn failure that created no helper can settle as `startup` in that invocation. An ambiguous interrupted start remains blocking.
- [ ] The registered helper runs `process.execPath --import tsx <directory>/server/overseer.ts pass` with the pinned directory as cwd, stdin ignored and the pass in the helper’s group. Require `tsx` to resolve through the release’s `node_modules/tsx`, allowing pnpm package links. An ancestor-only loader is a startup failure. Build the pass environment from `OVERSEER_ROOT`, optional normalized `OVERSEER_OFFICE_URL`, `PATH`, `HOME` and `NODE_ENV=production`. The pass entry establishes its own private `OFFICE_DATA_ROOT`.
- [ ] Give the supervised pass its own IPC channel to the helper for phase markers. Keep the launcher’s authorization channel private. In `server/overseer.ts`, emit optional markers immediately before the bootstrap imports at line 27 and after constructing the machine, just before `runPass`. Preserve the direct CLI’s stdout, exit codes and bootstrap import boundary. The helper relays phase markers and reports the actual candidate `exit` event, code and signal to the outside launcher. Drain stdout and stderr continuously, retaining at most the last 64 KiB of each. Bound the final drain independently of stream `close`.
- [ ] On pass exit observed before the deadline, capture the exit facts and disarm the pass timer immediately. Inspect the group while the trusted helper is still its leader. If the helper is the sole remaining member, let it exit. If other members remain, start the owned-group stop sequence immediately, including when the pass exited zero and descendants still hold its pipes. Time spent cleaning up an exited pass cannot turn it into a deadline hang.
- [ ] Use one idempotent stop sequence for pass exit with surviving members, deadline expiry, launcher shutdown and parent IPC loss. Send TERM to the identified group, allow up to 10 seconds and escalate to KILL if needed after rechecking identity. The helper handles TERM long enough to preserve the escalation target. It can exit promptly once it is the sole member. On parent loss it carries out bounded cleanup of its own group. Only the outside launcher, a recovering launcher or the operator can confirm disappearance. The outside launcher polls for `ESRCH` for up to 5 seconds. An inconclusive observation retains `current` and blocks dispatch.
- [ ] When the pass deadline fires first, latch `hang`. Before the first cleanup signal, atomically save the counted kind on `current`, increment the counters and publish one history record for the UUID. Exit facts can be null while the group is alive. On confirmed absence, clear `current` and complete any available exit facts on that same record. If the save fails, still perform bounded cleanup and report the storage error. Recovery of a saved hang must never add `lost`, `orphan` or a second hang for that UUID.
- [ ] For an ordinary completion, classify from the pass’s own exit and final record after confirmed group absence. A spawn or local-loader failure, exit 2 or observed bootstrap failure is `startup`. A post-start failed exit or signal is `exit`. For a legacy entry without markers, use the recording-error diagnostic at `server/overseer.ts:35` to distinguish its exit 1 from a bootstrap failure. An ambiguous legacy signal is `exit`. Exit 3 is `locked`. An intentional launcher shutdown is `interrupted`.
- [ ] Exit zero requires a complete final stdout record matching `PassRecord` in `server/overseer/runner-state.ts:43` plus the expected private `officeDataRoot`. Validate the pass’s own UUID, timestamps, recognized outcome, bounded detail and optional fields. The launcher attempt and the pass have separate UUIDs. Missing, truncated, malformed or unrelated output is `exit`. A valid record, including `service-down`, `paused` or `stopped`, is `success` once the group is absent. This applies when cleanup had to stop descendants after that pass exited.
- [ ] Increment `consecutiveFailures` for `config`, `pin`, `startup`, `exit`, `hang`, `lost` and `orphan`. Reset it on `success`. `locked` and `interrupted` preserve it. If cleanup after an ordinary exit cannot confirm absence, retain `current` with the observation. Charge an established pass failure under its own kind, or charge `orphan` once for otherwise successful or locked completion with unresolved cleanup. Never publish a success reset in that case. Store kind, UUID, start, duration, available exit facts and bounded outcome/detail in `last` and `recent`. Later blocked ticks update the observation only. Emit one bounded failure summary. The pass owns STOP, pause, its pass lock and its outage journal.
