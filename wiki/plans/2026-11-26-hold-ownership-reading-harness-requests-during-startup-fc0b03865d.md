# Hold ownership-reading harness requests during startup

Implement fix A for JFusco/the-office#636. A replica’s cold read hit `context-deadline` after 34.5 seconds on a 50 MB transcript. Seven subsequent warm reads completed. The live GH-3 request was claimed 47 seconds after restart and blocked. Its precise 04:47 trigger remains inferred because the inventory reads were not recorded and a reviewer was streaming. Phase 5, the Overseer, owns the separate live resume. [Issue decision](https://github.com/JFusco/the-office/issues/636#issuecomment-7183638410)

## Implementation

- [ ] In `server/workers/session-bridge.ts`, initialize `SessionBridge.firstCompleteAt` to `''` per instance. At the publication at the end of `read()` around line 115, assign the new inventory to `current`. In the same synchronous step, if its raw coverage is complete and the marker is empty, copy its `observedAt` into `firstCompleteAt`. Return that inventory. Every later read still publishes its own result, including incomplete results. A full scan that has already expired counts for startup. `forProject()` applies the existing 45-second freshness test from observation start.
- [ ] Add `server/scheduling/inventory-startup-wait.ts`. Give `inventoryStartupWait` the store, request and optional `Pick<SessionBridge, 'firstCompleteAt'>`. Return `null` unless the request is `queued` and `bridge?.firstCompleteAt === ''`. For a matching form return `waiting`, owner `Office`, `nextCheckAt: null`, and reason `Waiting for the first complete session inventory since the Office started`.
  - Match `resume-discovery`, `reconcile-implementation`, `reconcile-validation`, `adopt-candidate`, `reconcile-scope-repair` and `cleanup-merged-candidate` by action. This includes saved `adopt-candidate` requests with an empty head.
  - Match `reconcile-preparation` and `reconcile-closeout` when `request.head` is nonempty. Their empty-head forms keep their ordinary eligibility.
  - For `reconcile-base-update`, skip an empty head. Find the first non-cancelled job for `request.key`, as `reconcileBoardPreflight()` does. Only if its head equals `request.head`, consult `boardPreflightCandidate(store, job)` from `server/delivery/recovery/board-preflight.ts`. Hold the request if the returned candidate names that head. A stopped-worker ID, a missing candidate or a mismatched head goes to normal selection. If the local candidate read throws for a matching head, hold only that request during startup. Once the bridge opens, its handler owns any error. All other actions return `null`.
- [ ] In the reconciliation loop at `server/scheduling/scheduled-work.ts:114`, add the helper as the nullish fallback after `history(...)`, with `requestResolved(...)` first. Pass `coordinator?.sessionBridge`. `add()` applies pause and drain, and `withActiveClaims()` preserves running and stopping claims. The projection retains the request ID, status, enqueue time and repair binding. `selectWork()` can select another runnable item in the same project and lane on that pump.

## Scope and operation

- [ ] Use the bridge `Offices` already gives every coordinator. The regular pump runs every two seconds. The 15-second tick refreshes the bridge when polling is enabled and the fence permits the tick. Any existing caller’s completed refresh can open the gate. With polling disabled, progress depends on another such caller. Persistent incomplete coverage leaves matching requests visibly waiting with no fixed deadline.
- [ ] Keep execution on `executeRequest()` and the existing handler callbacks. They refresh and call `forProject(store, request.key, request.id)` with the current-worker exclusion. A repair resume or IT request using a matching form keeps its original identity while waiting. Intake reviews, feature assessments, delivery jobs, CEC work and independent IT checks keep their own admission paths.
- [ ] Add one bullet beside the session-inventory coverage description in `docs/office-process.md`. Document the request forms above, the first complete publication, and the ticket-specific check at execution. A startup wait alone produces no stopped-work subject. A separate hold on the request key can produce an expected hold subject. Pause or drain produces the project subject.
