# Releases and incident recovery

The deploy controller uses exact-commit release artifacts and an idle fence so a release can be installed with a durable record of the active service revision. The incident ledger records why work stopped, connects a repair to a release, and verifies the result from work resumed after that release.

A resume after a fix goes through one of the Office's existing handlers, named by the fix's route, once per subject and fix. Every route is dispatched except `retry-checkpoint` and `reconcile-maintenance`, which are left out by decision for the reasons their inventory rows give. The last route added was [the assignment review's resume](../journal/2026-11-24-assignment-review-resume.md), which keeps the review's recovery counters and replenishes no spent budget.

The controller pin can lag behind the service release, and the pinned release validates the local config with its own rules as it starts. Every launch therefore [checks the controller's start-up first](../journal/2026-11-27-controller-start-check.md): a config that release rejects is refused with nothing written, instead of leaving a STOP.

These changes landed as separate increments. The fence and release identity precede the controller. Incident observation and repair binding precede outcome verification. A merged fix and an observed running release provide different evidence.

An incident's identity is its cause's fingerprint. For a cause the harness wrote, that fingerprint includes its normalized text, in which occurrence details (paths, ticket keys, identifiers, times and numbers) become placeholders. A detail left in the text splits one cause into many incidents, as GitHub request IDs did until [rate-limit stops were grouped](../journal/2026-11-24-rate-limit-incident-grouping.md).

Incident evidence is redacted before anything keeps it. Where an edit to it begins and ends depends on the JSON string depth of the text. That depth is read once from the original text, and those edits are chosen there before the shared sanitizer runs, so [no credential survives a serialized shape](../journal/2026-11-26-evidence-redaction-gaps.md) and the result never depends on an earlier edit's offsets.

The Overseer's runner is a separate process that observes and reports. [Phase 6a](../journal/2026-11-25-overseer-runner-skeleton.md) reads the Office over loopback `GET`s, keeps one incident in flight and journals outages in its own folder. It is the one authorized exception to the shared-runtime rule. [Phase 6b](../journal/2026-11-26-overseer-phase-6b-runner-budgets.md) added the budget admission every future model call must pass: a ledger of reservations held until a matching receipt settles them, round and daily limits, required timeouts, and a daily ceiling on list-price estimates, which are not bills on the subscription logins the runner uses. [Phase 6c](../journal/2026-11-26-overseer-phase-6c-launcher.md) added the launcher a person installs as a LaunchAgent: every two minutes it runs one pass from a pinned, verified release in a process group of its own, stops that group at the deadline and counts each attempt once. [Phase 6d](../journal/2026-11-26-overseer-phase-6d-forwarding.md) lets the runner report to the Office. Its journaled outages are recorded on one `runner` incident under their journal IDs, and it reports whether it is running, paused or stopped. Each report goes through its own Effects, and a dispatched one is only ever read back. The Office serves notices for an open outage and a stopped runner in every project's outbox. A [helper fix](../journal/2026-11-26-overseer-helper-ipc-send.md) keeps the launcher's helper alive through a failed send to a dying launcher, so it still stops its pass's group. [Phase 7a](../journal/2026-11-26-overseer-phase-7a-worker-environment.md) began isolated research and triage. It gave future model workers an environment built from nothing, through the shared runner's `replaceEnv`, and private folders per run, named by the reservation that admitted it. [Phase 7b](../journal/2026-11-26-overseer-phase-7b-worker-sandbox.md) defined the outer sandbox every worker must run in: a policy that denies reads from `/` and reopens only the run's snapshot and folders, a wrapper with no executor of its own, and a qualification battery whose receipts bind each reader profile. It ships closed, with the runtime not installed until Joe approves it, and records a command-capable Codex reader as unqualified because Seatbelt does not nest on this Mac. [Phase 7c](../journal/2026-11-26-overseer-phase-7c-triage-corroboration.md) defined the triage verdict and the blind second opinion: one frozen input for both providers, a verdict published only once the ledger settles it against its launch session, agreement on substance, and six ordered rules that keep any affirmed block and admit a repair only on two agreeing, supported, current defects. [Phase 7d](../journal/2026-11-26-overseer-phase-7d-runner-playbook.md) seeded the runner playbook: advisory guidance, selected through the Office's own lesson selector with relabelled lines, frozen into the shared input, and never a citable source. [Phase 7e](../journal/2026-11-27-overseer-phase-7e-reader-sign-ins.md) built the gated reader call on separate runner sign-ins: every gate before admission, release of a call proven never dispatched, Codex refreshes published only with trusted evidence, stops keyed to sign-in generations, and both readers still unqualified pending host qualification.
